# Implementation Plan

Two Go binaries: `tillandsia` (CLI) and `tillandsia-init` (init system).
SSH-based deployment to a VPS. Caddy for TLS. Litestream for durable SQLite.

## Architecture

```
┌─ Your Machine ─────────────────────────────────┐
│  tillandsia deploy                              │
│    ├─ Read tillandsia.yaml / Procfile           │
│    ├─ Build Docker image                        │
│    ├─ Wrap with init system                     │
│    ├─ docker save | ssh docker load             │
│    └─ SSH: run the container                    │
│                                                 │
│  tillandsia server setup                        │
│    └─ SSH: install Docker, prep dirs,           │
│         store Litestream creds in server config │
└─────────────────────────────────────────────────┘

┌─ VPS ───────────────────────────────────────────┐
│  Docker container:                               │
│  ┌──────────────────────────────────────────┐    │
│  │  tillandsia-init (PID 1)                 │    │
│  │    ├─ Restore DB from Litestream         │    │
│  │    ├─ Start Litestream replication       │    │
│  │    ├─ Start user services                │    │
│  │    ├─ Generate Caddy config              │    │
│  │    ├─ Start Caddy (after health checks)  │    │
│  │    └─ Management API (:8080/mgmt/*)      │    │
│  │                                          │    │
│  │  ├─ Caddy (TLS, reverse proxy)           │    │
│  │  ├─ Litestream (SQLite → S3/R2/B2)      │    │
│  │  └─ User app (web, worker, cron)         │    │
│  └──────────────────────────────────────────┘    │
│  Persistent volume: /data/ (SQLite DB + config)  │
└──────────────────────────────────────────────────┘
```

## Design Decisions

| Decision | Choice | Rationale |
|---|---|---|---|
| Language | Go | Single binary, great cross-compilation, excellent for systems work |
| CLI framework | Cobra | Standard Go CLI library, good ergonomics, wide adoption |
| SSH library | `golang.org/x/crypto/ssh` | Standard library, well-maintained, supports key-based auth |
| Container runtime | Docker | Universal, pre-installed on most VPS images, well-understood |
| Image transfer | `docker save/load` via SSH pipe | Free tier, no registry needed. Registry = pro feature |
| Config format | `tillandsia.yaml` + `Procfile` | Heroku-inspired, familiar pattern |
| Reverse proxy | Caddy | Automatic TLS, simple config, Go binary |
| Database backup | Litestream | Continuous SQLite replication to S3-compatible storage |
| DNS | Caddy HTTP-01 (user creates A record) | Dead simple, no hosted infra needed. Hosted ACME zone = future |
| Litestream creds | Generated by provider, stored in server config | User never touches them. Provider creates bucket + keys atomically |
| Agent support | `--json`, `--yes`, stdout/stderr discipline | Built in from day 1, not retrofitted |
| Auth middleware | Caddy OAuth (proxy layer) | Handled by init system, no app code changes needed |
| Server provisioning | Unified provider: one token creates VPS + bucket + DNS | Every cloud has these primitives. Portable by design |

### Phase 2 — SSH Module

**Goal:** CLI can connect to a remote server, run commands, and transfer files over SSH.

**Tasks:**

- Implement SSH connection manager:
  - Key-based authentication (default `~/.ssh/id_rsa`, configurable path)
  - Password-based authentication (fallback, with prompt)
  - Connection caching (reuse sessions for multiple commands)
  - Configurable port, user, host key verification
- Implement remote command execution:
  - Run a command and capture stdout/stderr
  - Stream output in real-time (for `tillandsia logs`)
  - Return exit code for error handling
- Implement file transfer:
  - Pipe data through SSH (for `docker save | ssh docker load`)
  - SCP for small files (config files, env files)
- Implement connection test:
  - Verify SSH connectivity
  - Verify Docker is installed and running
  - Return structured error on failure

**Key interfaces:**


### Phase 4 — Init System (`tillandsia-init`)

**Goal:** `tillandsia-init` runs inside the container, starts processes, generates Caddy config, manages Litestream, and exposes a management API.

**Tasks:**

- Implement Procfile parser:
  - Parse `type: command` format
  - Validate service types (web, worker, cron)
  - Extract command string for each service
- Implement process supervisor:
  - Start processes in order (Litestream first, then services, then Caddy)
  - Monitor each process (goroutine per process)
  - Restart on crash (configurable retry limit)
  - Forward signals (SIGTERM → graceful shutdown)
  - Collect stdout/stderr from each process
  - Log with timestamp and service name prefix
- Implement Litestream lifecycle:
  - Generate Litestream config from env vars
  - Restore from latest snapshot on startup (blocking, with timeout)
  - Start Litestream replication process (background)
  - Monitor replication lag
  - Flush on shutdown
- Implement Caddy config generation:
  - Read domain from env var
  - Generate Caddyfile: `domain { reverse_proxy localhost:$PORT }`
  - If no domain, generate `:80 { reverse_proxy localhost:$PORT }`
  - Handle custom Caddyfile (user-provided, override)
  - Support auth middleware config (future)
  - Write Caddyfile to `/etc/caddy/Caddyfile`
- Implement health checks:
  - Wait for web service to respond on `$PORT`
  - Configurable timeout and retry interval
  - Only start Caddy routing after health check passes
  - Report health status via management API
- Implement management API:
  - `GET /mgmt/health` — returns liveness and readiness, Litestream lag
  - `POST /mgmt/shutdown` — initiates graceful shutdown
  - `GET /mgmt/identity` — returns instance info
  - HTTP server on port 8080 (internal only)
- Implement graceful shutdown:
  - On SIGTERM or `/mgmt/shutdown`:
    1. Stop accepting new connections (Caddy)
    2. Send SIGTERM to user services
    3. Wait for services to exit (configurable timeout)
    4. Flush Litestream WAL
    5. Exit
- Implement zero-downtime handoff (basic):
  - On startup, check for existing container's management port
  - If found, send shutdown request to old container
  - Wait for old container to exit
  - Start normally

**Key interfaces:**

```go
type Supervisor struct { /* ... */ }

func NewSupervisor(config *Config) *Supervisor
func (s *Supervisor) Start(ctx context.Context) error
func (s *Supervisor) Shutdown(ctx context.Context) error
func (s *Supervisor) Health() HealthStatus
```

**Verification:**
- `tillandsia-init` starts with a Procfile and reaches healthy state
- Processes restart on crash
- Caddy config is generated correctly
- Litestream restores and replicates
- Health endpoint returns correct status
- SIGTERM triggers graceful shutdown
- Zero-downtime handoff works (old container → new container)

### Phase 5 — Deploy Pipeline

**Goal:** `tillandsia deploy` builds, wraps, transfers, and runs the container. `tillandsia logs`, `tillandsia status`, `tillandsia env` all work.

**Tasks:**

- Implement Docker build:
  - Run `docker build` with user's Dockerfile and context
  - Tag image as `tillandsia/<app-name>:<timestamp>`
  - Handle build failures with clear error messages
  - Support build args from config
- Implement image wrapping:
  - Create a wrapper Dockerfile:
    ```dockerfile
    FROM user-image
    COPY tillandsia-init /usr/local/bin/
    COPY caddy /usr/local/bin/
    COPY litestream /usr/local/bin/
    ENTRYPOINT ["tillandsia-init"]
    ```
  - Build the wrapped image
  - Tag as `tillandsia/<app-name>:<timestamp>-wrapped`
  - Keep previous image tag for rollback
- Implement image transfer:
  - `docker save <image> | ssh <server> docker load`
  - Show progress for large images
  - Handle transfer failures with retry
- Implement container lifecycle:
  - Stop old container (if exists):
    - `docker stop --time 30 <app-name>`
    - `docker rm <app-name>`
  - Start new container:
    - Mount volume: `/var/lib/tillandsia/<app>/data:/data`
    - Mount env file: `/var/lib/tillandsia/<app>/env:/run/tillandsia/env`
    - Set env vars from config + Litestream creds from server config
    - Publish port 80 and 443
    - `docker run -d --name <app> --restart unless-stopped -p 80:80 -p 443:443 ... <image>`
  - Wait for health check (management API)
  - Report success/failure
- Implement `tillandsia deploy`:
  - Orchestrate all steps: read config → build → wrap → transfer → run
  - Progress output (spinners for each step)
  - `--dry-run` flag (show plan without executing)
  - `--server` flag (target specific server)
  - `--json` flag for agent output
  - `--rollback` flag (re-deploy previous image)
  - On failure, print actionable error message
- Implement `tillandsia status`:
  - SSH: `docker inspect <app-name>` and `docker logs --tail 20 <app-name>`
  - Parse container state, health, uptime
  - Query management API for Litestream lag
  - `--json` flag
- Implement `tillandsia logs`:
  - SSH: `docker logs --tail <n> --follow <app-name>`
  - Stream output in real-time
  - `--tail` flag (default 50)
  - `--follow` / `-f` flag (default true)
  - `--json` flag (JSON lines format)
  - Clean exit on Ctrl+C
- Implement `tillandsia env`:
  - `env set <key>=<value>` — write env file on server, restart container
  - `env get <key>` — read specific var from env file
  - `env rm <key>` — remove var, restart container
  - `env list` — list var names (no values by default)
  - `env export` — dump all vars as `key=value` or JSON
  - All commands support `--server` and `--json`
  - Env file stored at `/var/lib/tillandsia/<app>/env`
  - Container restarts automatically after env change

**Deploy pipeline pseudocode:**

```
func Deploy(ctx, app, server) error {
    config := ReadConfig(app.dir)
    serverConfig := LoadServer(server)

    // Step 1: Build user image
    userImage := BuildImage(ctx, config)
    defer RemoveImage(userImage)

    // Step 2: Wrap with init system
    wrappedImage := WrapImage(ctx, userImage, config)

    // Step 3: Transfer to server
    TransferImage(ctx, serverConfig, wrappedImage)

    // Step 4: Stop old container
    StopContainer(ctx, serverConfig, config.Name)

    // Step 5: Start new container
    env := MergeEnv(config.Env, serverConfig.LitestreamCreds)
    StartContainer(ctx, serverConfig, config.Name, wrappedImage, env)

    // Step 6: Wait for health
    WaitForHealthy(ctx, serverConfig, config.Name)

    return nil
}
```

**Verification:**
- End-to-end deploy: `tillandsia init` → `tillandsia server add` → `tillandsia server setup` → `tillandsia deploy` → app is running
- `tillandsia logs` streams app output
- `tillandsia status` shows correct state
- `tillandsia env set` updates env and restarts container
- `tillandsia deploy --dry-run` shows plan without executing
- `tillandsia deploy --rollback` re-deploys previous image

### Phase 6 — Polish

**Goal:** Production-quality UX, error handling, zero-downtime, provider interface.

**Tasks:**

- Rich terminal output:
  - Spinners for long-running operations (build, transfer, deploy)
  - Progress bars for image transfer
  - Color-coded output (green for success, red for errors, yellow for warnings)
  - Use `charmbracelet/bubbletea` or `charmbracelet/bubbles` (or `charmbracelet/lipgloss` + `briandowns/spinner`)
  - Disable automatically when `--json` or `--quiet` is set
- Error handling:
  - Define error types for all failure modes
  - Actionable error messages ("Server not reachable: check the IP and SSH key")
  - Categorized error codes (see agent.md)
  - Stack traces in debug mode (`--debug` flag)
- Zero-downtime deploys (full):
  - New container starts alongside old container on same Docker network
  - New container discovers old container's management port
  - Cooperative handoff via management API
  - Old container drains connections, flushes Litestream, exits
  - New container takes over traffic
  - Fall back to rolling update if zero-downtime fails
- DNS guidance:
  - `tillandsia deploy` prints exact DNS record to create
  - `tillandsia dns` command: show DNS instructions for current config
  - Verify DNS resolution before deploy (optional)
- Pluggable provider interface:
  - The provider creates **everything** from a single API token: a VPS, an S3-compatible
    bucket, access keys for the bucket, and DNS records. These are the same primitives
    available in every cloud — DigitalOcean has Droplets + Spaces + DNS, AWS has
    EC2 + S3 + Route53, GCP has Compute Engine + Cloud Storage + Cloud DNS.
  - Define `Provider` interface:
    ```go
    type Provider interface {
        // Name returns the provider name (e.g. "digitalocean", "aws")
        Name() string

        // Provision creates everything needed: VPS, bucket, DNS.
        // Returns the server info with all generated credentials.
        Provision(ctx context.Context, spec *ProvisionSpec) (*ProvisionResult, error)

        // Deprovision tears everything down: VPS, bucket, DNS records.
        Deprovision(ctx context.Context, serverID string) error

        // GetStatus returns the status of all provisioned resources.
        GetStatus(ctx context.Context, serverID string) (*ProvisionStatus, error)
    }

    type ProvisionSpec struct {
        Name       string // app/server name
        Region     string // e.g. nyc1, us-east-1
        Size       string // e.g. s-1vcpu-1gb, t3.micro
        Domain     string // optional domain for DNS record
        ProviderToken string // the user's cloud API token
    }

    type ProvisionResult struct {
        ServerID     string // cloud provider's server/resource ID
        ServerIP     string // public IP of the VPS
        ServerUser   string // SSH user (usually root)
        SSHKey       string // auto-generated SSH private key

        BucketName   string // bucket name for Litestream
        BucketURL    string // full S3 URL for the bucket
        BucketRegion string // region the bucket lives in
        AccessKeyID  string // generated access key
        SecretKey    string // generated secret key

        Domain       string // domain with A record pointing to ServerIP
    }
    ```
  - Implement DigitalOcean provider:
    - Create a Spaces bucket (S3-compatible) with access keys
    - Create a Droplet with an auto-generated SSH key
    - Create DNS A record pointing the domain to the Droplet IP
    - Return `ProvisionResult` with all credentials
    - Deprovision: delete droplet, delete bucket, delete DNS records
    - Uses `digitalocean/godo` SDK
  - Provider registry and CLI integration:
    ```bash
    # Single command provisions everything:
    tillandsia server provision do \
      --name my-app \
      --region nyc1 \
      --size s-1vcpu-1gb \
      --domain my-app.example.com \
      --token dop_v1_...

    # Or use TILLANDSIA_DO_TOKEN environment variable
    export TILLANDSIA_DO_TOKEN=dop_v1_...
    tillandsia server provision do --name my-app
    ```
  - The provider auto-generates SSH keys, creates the bucket, generates access keys,
    creates the DNS record, and stores everything in the server config. The user
    never sees or manages any of these intermediate credentials.
  - Provider interface lives in the open core. Community implementations for AWS,
    GCP, Linode, Hetzner, etc. are straightforward.
  - The SSH-based `tillandsia server add` + `tillandsia server setup` path still
    works for users who want to bring their own server.
- `tillandsia init` polish:
  - Detect more frameworks (Next.js, Django, Rails, Gin, etc.)
  - Generate more sophisticated Procfiles
  - Offer to configure Litestream during init
- Documentation:
  - README with quickstart (3 steps: install, add server, deploy)
  - Full CLI reference (`tillandsia help <topic>`)
  - Architecture overview
  - FAQ

**Verification:**
- Full end-to-end with zero-downtime: deploy v1, deploy v2, no dropped requests
- `tillandsia server provision do` creates a DigitalOcean droplet and sets it up
- `tillandsia help` renders all docs correctly
- Error messages are clear and actionable
- `--json` output is valid and complete for every command

## Future Considerations (Post-Phase 6)

### Hosted Registry
A container registry for faster deploys. Paid feature. The open core uses SSH pipe
by default.

### Hosted Control Plane
The commercial layer: team management, deploy dashboard, centralized logging,
backup management UI, billing. Runs on top of the open core.

### Hosted DNS Zone
`*.tillandsia.app` subdomains with DNS-01 ACME challenges. No domain purchase needed.
Paid feature.

### mTLS / SPIFFE
Service identity with short-lived certificates. Secure inter-service communication.
Local development as a mesh participant. Enterprise feature.

### Custom OAuth / OIDC
Enterprise identity providers (Okta, Ping, internal IdPs). Enterprise feature.

### Deployment Policies
Approval gates, deploy windows, rollback policies. Enterprise feature.
